# 2.9｜Skill进阶：如何团队共享一个 Skill
> Skill 模块（七十二变之一变：让 Agent 获得专长）｜状态：待确认｜2026-08-27

## 课眼
Skill 的本体是一个 `.md` 文档，打包后仍然是 `.md`。个人试用时可以直接发文件；团队长期使用时，把它放进共同维护的 GitHub 仓库，让仓库主分支成为“真正的、最最最新的版本源”。

- **主标题**：Skill进阶：如何团队共享一个 Skill
- **小副标题**：把 Skill 从“发文件”升级成团队共同维护的最新版本
- **当天产出**：一个团队共享 Skill 仓库 + 一次版本同步记录

## 学员痛点
老板或技能发起人不断完善 Skill，但员工手里的旧 `.md` 不会自动更新。反复发文件、改文件名、写提示词，容易出现版本漂移，出了问题也难以回退。

## 一、先记住：Skill 就是可维护的 `.md`

Skill 的核心通常写在 `SKILL.md` 或其他 Markdown 文件里。它可以打包、下载、复制，但不会变成不可读的黑盒；规则、示例、自检和边界都能继续阅读与维护。正因为是普通文本，谁改了什么、什么时候改、为什么改，都可以交给版本管理记录。

## 二、初级方案：直接把文件发给新员工

新员工入职时，把已经验证过的 `.md` 发给他，放进自己的 Agent Skills 目录，再跑一个小任务确认能用。这条路上手快，适合临时合作或还没准备好 GitHub 的小团队。

文件至少要写清来源、版本号和更新时间，例如 `brand-writer-v1.2.md`。如果所有文件都叫 `SKILL.md`，两周后就没人知道哪一份是最新版。

## 三、为什么直接发文件会失控

1. 老板本地迭代后，员工电脑里的副本不会自动变化。
2. 每次更新都要重新发送并提醒替换旧版。
3. 不同员工可能各自修改，版本和文件名越来越乱。
4. 出问题时无法快速回答改动来源，也没有可靠回退点。

## 四、一张图看懂：中心仓库才是最新版本源

```text
                 老板/高管维护并验收
                            │ 提交
                            ▼
          ┌────────────────────────────────┐
          │ GitHub 中央仓库                 │
          │ 真正的、最最最新的 Skill 版本   │
          └────────────────────────────────┘
             ▲ 拉取       ▲ 拉取        ▲ 拉取
             │            │             │
           员工 A        员工 B       合作伙伴
             │            │             │
             └──同步到各自的 Agent Skills 目录──┘
```

所有人围绕同一个源头工作：负责人把验证过的迭代提交到仓库；其他人使用前先拉取最新版本，再同步到自己的 Agent。仓库主分支是团队判断“哪一版能用”的唯一依据。

## 五、推荐流程：改一次，大家同步

1. 创建一个私有仓库，例如 `company-skills`，按 Skill 分文件夹。
2. 设负责人。老板、高管或技能发起人负责合并版本和最终验收，其他成员通过 Issue 或 Pull Request 提议修改。
3. 负责人在副本或分支中迭代，用低风险任务测试规则、示例和自检。
4. 提交主分支时写版本号、更新时间和变更摘要；必要时打 tag，例如 `brand-writer-v1.3`。
5. 员工使用前从 GitHub 拉取最新 `SKILL.md`，核对版本号，再更新自己的 Agent。
6. 员工发现问题时记录输入、输出和建议，反馈给负责人，不传播未经确认的本地改版。

## 六、员工使用前的三秒检查

| 检查项 | 怎么确认 | 不通过怎么办 |
|---|---|---|
| 来源 | 链接指向公司 GitHub，而不是聊天附件 | 停止使用，先找负责人 |
| 版本 | 查看 `CHANGELOG.md`、tag 或文件头版本 | 拉取最新主分支 |
| 本地副本 | 确认 Agent 实际读取的路径 | 隔离旧副本后重新同步 |
| 权限 | 明确只读、提交或合并权限 | 没权限就提 Issue/PR |

## 七、仓库结构与安全边界

```text
company-skills/
├─ README.md
├─ CHANGELOG.md
├─ brand-writer/
│  ├─ SKILL.md
│  ├─ examples/
│  └─ tests/
└─ ppt-brand/
   ├─ SKILL.md
   └─ examples/
```

内部 Skill 优先使用私有仓库，按成员角色授予权限，不共用账号。不要提交客户隐私、密码、Token、API Key 或未脱敏素材。每次合并保留变更记录和可回退 tag；新版有问题时先回退到上一个已验收版本。仓库最新不等于本机已经同步，员工仍要在自己的 Agent 中做一次低风险验证。

## 直播演示

先把同一份 `SKILL.md` 发给两位学员，模拟老板更新后仍有人使用旧版；再创建 GitHub 私有仓库，完整演示负责人更新、提交、打 tag、员工拉取、本地版本核对和 Agent 低风险验证。

## 学员练习

选一个已经跑通的 Skill，创建私有 GitHub 仓库并上传 `SKILL.md`、README 和 CHANGELOG；让一位同事从仓库拉取并跑同一测试任务；负责人再提交一个小改动，团队核对版本号、变更记录和同步结果。

## 验收标准

- 能解释 Skill 为什么本质上是可维护的 `.md` 文档。
- 能说清直接发文件的初级方案以及版本漂移问题。
- 能画出“GitHub 中央仓库 = 真正最新版本源”的团队关系图。
- 能完成一次负责人提交、员工拉取、Agent 更新和低风险验证。
- 能设置私有仓库权限、变更记录、版本 tag 和回退路径。

## 配套模板

> 这份 Skill 的唯一最新版本源是：____。负责人是：____。主分支是：____。任何修改先在副本/分支中完成，并补充版本号、变更原因、示例和自检结果；负责人验收并合并后，其他成员再同步。每次使用前检查仓库版本和本地路径；发现问题先提 Issue，不在群里散发未经确认的 `SKILL.md`。
