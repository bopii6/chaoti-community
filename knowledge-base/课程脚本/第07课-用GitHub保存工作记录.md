# 第 07 课｜GitHub 的神奇用法
> 模块一 · ⑦ 成果管理 ｜ 状态：✅ 已确认 ｜ 2026-08-24

## 课眼（这一课存在的意义）
GitHub 不只是程序员放代码的地方，它更像一个公开的 AI 工作集市和项目档案库：你可以把 Agent 的每次成果保存下来，从别人仓库获取已经验证过的 Skill，研究优秀的 AI 项目，还能把静态网站发布成一个任何人都能打开的链接。

- **主标题**：GitHub 的神奇用法
- **小副标题**：保存记录、获取 Skill、发现 AI 项目、把网站上线
- **当天产出**：一个已发布到 GitHub 的 private 工作仓库、一份 Skill/AI 项目导读和一个网站上线方案
- **推荐工具**：GitHub Desktop（图形界面，不把命令行作为入门门槛）

## 学员痛点

「Agent 干完活，关掉就没了」「改坏了不知道怎么回去」「想找 Skill 不知道去哪找」「看到一个 AI 项目却不知道能不能用」「网站做好了却没有网址」。GitHub 不是程序员考试，而是给项目留记录、找能力、看案例和发布网站的基础设施。

## GitHub 的四种神奇用法

| 用法 | 你要做什么 | 最后得到什么 |
| --- | --- | --- |
| 1. 保存工作记录 | 把本地项目变成仓库，每次 Agent 完成一版就 Commit、Push | 可查看、可比较、可恢复的项目历史 |
| 2. 获取 Skill 技能 | 找到可信仓库，阅读 README 和 SKILL.md，再让 Agent 安装或调用 | 让 Agent 多一种专业工作能力 |
| 3. 找到优秀的 AI 项目 | 按主题搜索仓库，检查活跃度、文档、许可证和运行要求 | 可学习、可试用、可改造的项目样本 |
| 4. 把网站上线 | 把网站代码放进仓库，用 GitHub Pages 或其他部署平台连接仓库 | 一个可以分享给别人的线上网址 |

## 用法一：保存工作记录

这是本课最基础、也最常用的用法。Agent 改文件之前和之后，都留下一条有名字的版本记录；你可以回看它做过什么，也可以在改错时恢复上一版。下面的「第 1 步」到「第 12 步」会完整演示如何用 GitHub Desktop 把本地项目发布到网上。

## 用法二：获取 Skill 技能

1. 在 GitHub 搜索你需要的能力，例如写作、视频、数据分析、网页开发或项目管理 Skill。优先看作者、README、最近更新时间、使用说明和许可证，不要看到一个仓库就直接运行。
2. 打开仓库后先找 `README.md`、`SKILL.md` 或 `skills` 文件夹，确认它支持哪个 Agent 工具、需要哪些依赖、会读写哪些文件。
3. 把仓库链接或具体的 `SKILL.md` 交给 Agent，让它先解释这个 Skill 做什么、会执行什么操作、需要哪些权限，再决定是否安装。
4. 安装前让 Agent 做安全检查：列出将创建/修改的文件、需要执行的命令、会发送到哪些外部服务；涉及登录、密钥、付费和上传时由老板自己确认。
5. 装好后用一个低风险任务试跑，并把有效配置和使用方式写回自己的项目仓库。不要为了「收藏」一次性安装几十个 Skill。

## 用法三：找到优秀的 AI 项目

1. 先把需求说成关键词：例如 `browser automation`、`knowledge base`、`local RAG`、`video agent`、`content workflow`，再在 GitHub 搜索。
2. 打开项目主页先看四项：README 是否能让新手跑起来、最近是否仍在更新、Issue 是否有人回应、许可证是否允许你的使用方式。Star 数只能作为线索，不能代替实际检查。
3. 确认系统要求、模型 API、费用、数据是否会离开本机，以及项目是否需要管理员权限。先在测试文件夹或虚拟环境运行，不要直接放进重要项目。
4. 让 Agent 做项目导读：它解决什么问题、适合谁、最小运行步骤是什么、有哪些风险、哪些文件值得先读。读懂后再决定是直接使用、借鉴思路，还是只保存链接。
5. 优秀项目的价值不只在于下载使用，也在于学习它的目录结构、提示词、Skill、README 和验收方法。

## 用法四：把你的网站上线

1. 先把网站代码整理成一个独立 GitHub 仓库，至少包含入口文件（例如 `index.html`）、样式、脚本和 `assets`；先在本地打开确认没有明显错误。
2. 纯静态网站可以使用 GitHub Pages：进入仓库 `Settings → Pages`，在 Build and deployment 中选择从分支部署，选择 `main` 分支和 `/(root)` 目录，保存后等待 GitHub 生成网址。
3. 如果项目需要构建命令、环境变量或后端服务，GitHub 负责保存代码，部署可以交给 Cloudflare Pages、Vercel 等平台；连接仓库后，每次 Push 都可以触发重新部署。
4. 上线前检查仓库是否应该 private、域名是否需要绑定、API Key 是否误放进前端、图片路径是否使用相对路径，以及手机端是否能正常打开。
5. 上线后保留一个稳定版本提交。以后 Agent 修改网站，先在本地或预览部署验证，再 Push 到正式分支；不要把「代码上传成功」误认为「网站已经可用」。

## 先把三个词弄明白

- **Git**：装在电脑里的版本记录工具，负责观察文件变化、保存一版一版的快照。
- **GitHub**：互联网上的代码和文件托管网站，负责保存远程副本、浏览历史和跨设备访问。
- **仓库（repository / repo）**：一个项目的专属文件夹，里面有项目文件，也有这个项目的提交历史。

可以把它想成数字员工的工作档案：本地项目是员工的办公桌，Git 是工作日志，GitHub 是放在网上的保险柜，GitHub Desktop 是不用背命令的图形界面。

## 这节课的完整路线

1. **第一步**：选一个不含密码和隐私的本地项目，整理文件并确认能正常打开。
2. **第二步**：注册/登录 GitHub，安装 GitHub Desktop，并让它连接你的账号。
3. **第三步**：在 GitHub Desktop 添加本地项目，创建第一次提交（Commit）。
4. **第四步**：点击 Publish repository，把项目发布到 GitHub 的远程仓库（Push）。
5. **第五步**：打开网页确认文件已经在线，再练习下一次修改、提交、推送。
6. **第六步**：查看历史和差异；出现问题时，恢复上一版或让 Agent 根据记录修复。

## 第 1 步：选择和整理要保存的项目

1. 先选一个练习项目，例如课程网页、个人简历、一个 Markdown 知识库或一个小脚本。不要一开始就拿公司机密、客户资料或正在上线的核心项目练习。
2. 确认项目在一个独立文件夹里，例如 `C:\Users\你的名字\Documents\my-first-project`。文件夹名称尽量用英文、数字和短横线，避免空格和特殊符号。
3. 打开项目，确认它目前能正常使用；如果 Agent 刚改完，先把当前版本复制一份到本地备份文件夹。
4. 检查是否含有密码、API Key、浏览器 Cookie、客户名单、身份证件、支付信息或 `.env` 文件。敏感内容不能上传到 GitHub，即使仓库设为 private 也不要把它当成保险。

## 第 2 步：注册 GitHub 账号并完成基础设置

1. 打开 [GitHub 官方网站](https://github.com)，点击 `Sign up`，使用自己的邮箱注册并完成验证。用户名会出现在仓库链接里，建议使用容易识别、长期会使用的名字。
2. 登录后确认右上角头像显示的是自己的账号。课程只需要个人账号，不需要创建公司组织。
3. GitHub 的 `public` 仓库所有人都能看到，`private` 仓库只有你和被授权的人能看到。第一次练习建议创建 `private` 仓库。
4. 不要把 GitHub 密码、双因素验证码或 Personal Access Token 发给 Agent，也不要截图公开。需要授权时由你自己在官方窗口完成。

## 第 3 步：安装 GitHub Desktop

1. 在 [GitHub Desktop 官方页面](https://desktop.github.com/) 下载对应 Windows 或 macOS 版本，安装后打开。
2. 首次启动会出现 `Sign in to GitHub.com`，点击后在浏览器完成登录授权，再回到 Desktop。
3. 看到自己的头像或用户名，说明账号连接成功。GitHub Desktop 会使用 Git 完成本地记录，你不需要单独学习命令行，也不需要手动修改配置文件。

## 第 4 步：把本地项目加入 GitHub Desktop

1. 打开 GitHub Desktop，选择 `File → Add local repository`。
2. 点击 `Choose`，选中你的项目文件夹。GitHub Desktop 会扫描文件并显示 `Changes`（改动文件列表）。
3. 如果提示 `This directory does not appear to be a Git repository`，不要慌：点击 `create a repository` 或 `create a new repository`，把这个现有文件夹初始化为 Git 仓库。
4. 填写 `Name`（仓库名）和 `Local path`（本地路径）。练习项目可以勾选 `Initialize with a README`；如果文件夹已经有 README，不要重复生成。
5. 点击 `Create repository`。此时只是建立了本地记录，还没有发布到互联网。

## 第 5 步：完成第一次提交（Commit）

1. 在左侧 `Changes` 列表逐个看文件。确认没有 `.env`、密码、密钥或不应公开的资料；不确定的文件先取消勾选或移出项目文件夹。
2. 在左下角 `Summary`（必填）写清楚这一版做了什么，例如 `建立课程网页初始版本`、`整理第一批课程脚本`，不要只写 `update` 或 `修改`。
3. `Description`（可选）可以补充原因和下一步。
4. 点击 `Commit to main`。Commit 的意思是把当前这组改动写进本地工作日志；即使此刻没有网络，提交也可以完成。

## 第 6 步：发布到互联网上（Publish repository）

1. 第一次提交完成后，顶部会出现 `Publish repository`，点击它。
2. 检查 `Name`、`Description` 和 `Keep this code private`。小白练习建议保持 private；只有明确想开源时才取消勾选。
3. 点击 `Publish repository`，等待上传完成。这个动作会把本地仓库复制到 GitHub 账号中，称为 `push`（推送）。
4. 上传结束后点击 `View the repository on GitHub`，浏览器会打开类似 `https://github.com/用户名/仓库名` 的网址。把网址记录在项目说明或课程作业里，但不要把密钥放进链接参数。

## 第 7 步：在网页上确认项目真的保存好了

检查仓库页面的文件列表、README、最后提交时间和提交说明。点击提交记录，可以看到这次提交包含哪些文件；点击某个文件，可以查看在线版本。

注意：GitHub 网页上看得到，才说明已经推送成功。只在 GitHub Desktop 里 Commit、没有 Publish 或 Push，只是保存在本地，电脑坏了仍然可能丢。

## 第 8 步：以后 Agent 每完成一版，都按这套动作保存

1. 先让 Agent 说明它准备修改哪些文件、不会碰哪些文件；重要项目先让它只读检查。
2. Agent 完成后，在 GitHub Desktop 的 `Changes` 中检查差异（diff）：新增了什么、删掉了什么、有没有意外改到配置或隐私文件。
3. 确认无误后写一条具体 Summary，例如 `完成第七课 GitHub 入门教程`，点击 `Commit to main`。
4. 点击 `Push origin`，把本地提交推送到 GitHub。看到 Fetch/Pull/Push 状态恢复正常，再打开网页确认。
5. 一个可执行的节奏是：一个可验收的小版本 = 一个提交。不要把一周几十次改动攒成一个看不懂的提交。

## 第 9 步：查看历史和比较差异

点击 GitHub Desktop 左侧 `History`，可以按时间看到所有提交。每条记录都有时间、作者和 Summary；点击某条记录，右侧会显示它改了哪些文件。

在 GitHub 网页点击 `commits`，也能查看线上历史。点击某条提交的短哈希或标题，可以看到绿色新增、红色删除的具体差异。先看差异，再判断是否接受 Agent 的结果。

## 第 10 步：出问题时恢复上一版

1. 先停止 Agent 的继续修改，保存当前现场，不要直接覆盖或删除文件。
2. 在 `History` 找到最后一个正常提交，右键选择 `Revert Changes in Commit`（不同版本文字可能略有变化），让 GitHub Desktop 生成一个反向提交。
3. 检查反向提交的 `Changes`，确认它只撤销错误版本，再 `Commit` 并 `Push origin`。
4. 如果只是想把某个旧文件拿出来参考，可以在历史记录中打开该文件并复制内容，不要为了小问题回退整个项目。
5. 回退前先让 Agent 阅读提交差异并说明影响；数据库、线上配置和已经发送出去的消息不能靠 GitHub 自动撤回。

## 第 11 步：用网页上传的替代方法

没有安装 GitHub Desktop 时，可以在 GitHub 网页中新建仓库，点击 `Add file → Upload files`，把少量文件拖进去，填写提交说明后点击 `Commit changes`。这个方法适合第一次上传几个 Markdown 或图片，不适合频繁保存大型项目。

网页上传同样要检查隐私和密钥；文件数量多、需要看差异、需要回退时，还是使用 GitHub Desktop 更稳。

## 第 12 步：安全边界和协作规则

- 不要上传 API Key、密码、Token、`.env`、证书私钥、客户资料、身份证件、内部合同和未授权素材。
- 公开仓库适合教程、开源代码和可分享资料；个人工作记录默认用 private。
- 一个项目一个仓库，不要把所有个人文件夹一股脑上传。大文件、构建产物和缓存目录按需排除。
- README 写三件事：项目是做什么的、如何运行、当前进展是什么。
- Agent 可以帮你检查变更、生成提交说明、解释冲突，但账号登录、授权、公开仓库和上传敏感资料必须由老板自己确认。

## 现场演示（55 分钟）

1. 解释 Git、GitHub、仓库、Commit、Push、Pull、Revert；
2. 选择一个没有敏感信息的本地课程项目，完成 Add local repository、第一次 Commit 和 Publish repository；
3. 打开网页确认文件和提交记录，让 Agent 改一处文字，检查 diff、再次 Commit/Push，再用 Revert 恢复；
4. 从一个可信仓库找到 `SKILL.md`，让 Agent 做安全导读，列出权限、依赖和安装前检查；
5. 用 README、最近更新、Issue、许可证和运行要求筛选一个优秀 AI 项目；
6. 把一个静态网页仓库连接到 GitHub Pages 或部署平台，打开线上网址检查桌面端和手机端。

## 学员练习与交付物

完成一张《GitHub 四种用法记录表》：

- **保存记录**：检查文件 → GitHub Desktop 添加 → 第一次 Commit → Publish repository → 网页确认；
- **获取 Skill**：记录仓库链接、README/SKILL.md 摘要、权限和安装风险；
- **找 AI 项目**：记录项目用途、最近更新、Issue、许可证、依赖和是否值得试用；
- **网站上线**：记录仓库、部署方式、线上网址和桌面/手机端检查结果。

再让 Agent 修改一个小文件，完成 **看 diff → 写清楚提交说明 → Commit → Push → 查看历史**，最后用 `Revert` 恢复这次小改动，记录恢复前后的提交说明和差异。

## 验收标准

- 能用自己的话说出 GitHub 的四种用法；
- 能把本地项目发布成 private 仓库，并查看提交历史、差异和恢复上一版；
- 能从 GitHub 找到一个 Skill，读懂 README/SKILL.md，并在安装前列出权限和风险；
- 能按文档、活跃度、Issue、许可证、依赖和费用判断一个 AI 项目是否值得尝试；
- 能把一个静态网站部署上线，并区分「代码已上传」和「网址可访问」；
- 能在保存、安装、运行和部署前识别 API Key、隐私、授权和付费风险。

## 常见误区

- 以为 GitHub 只给程序员用，或者把 Git 和 GitHub 当成同一个东西；
- 只在本地 Commit，却忘了 Publish/Push，电脑坏了仍然没有网上备份；
- 第一次上传前没有检查 `.env`、API Key、客户资料和隐私文件；
- 从陌生仓库直接安装 Skill 或运行脚本，没有先读 README、SKILL.md、许可证和权限要求；
- 只看 AI 项目的 Star 数，不看最近更新、Issue、文档、依赖、费用和数据风险；
- 把代码 Push 到 GitHub 就以为网站已经上线，没有配置部署、域名和环境变量；
- 一出问题就删除仓库或覆盖文件，没有保留现场并先查看历史；
- 把 GitHub 当成数据库、云盘或线上部署平台；它保存项目版本，但不会自动撤销已经发出的消息或线上数据。
